Configuration and data types

GravitationalWaveBayes.Types.DetectorData — Type
DetectorData

Type alias for what this package's likelihood/kernel entry points accept as detector data: either a single LikelihoodData (single-detector) or AbstractVector{<:LikelihoodData} (multi-detector – one entry per detector, e.g. [h1_data, l1_data] for H1+L1).

Design choice: multi-detector data is represented as a plain Vector{LikelihoodData} rather than a new wrapping struct. Reasoning:

  • LikelihoodData already carries gps_time per entry; every multi-detector entry point (KernelFused.batched_log_likelihood_kernel!, RelativeBinning.build_relative_binning/ binned_log_likelihood_kernel!, DataIO.build_gwdata_multi) asserts all entries share the same gps_time (same physical event) rather than silently assuming it.
  • freqs/strain/psd may genuinely differ in length/grid per detector (independent data conditioning per detector is plausible even if today's real-data pipeline happens to produce matching grids for H1/L1) – there is no shared-shape invariant to hoist into a new type.
  • The one field that IS shared (gps_time, a single Float64) is cheap enough to duplicate per entry, and duplicating it keeps every LikelihoodData self-contained/independently constructible (e.g. by the existing, unchanged DataIO.build_gwdata) rather than requiring a two-step construction (build N LikelihoodDatas, then wrap). A new struct MultiLikelihoodData bundling gps_time once was considered and rejected for this reason.

GravitationalWaveBayes.Types.LikelihoodData — Type
LikelihoodData{F,S,P}

Single-detector frequency-domain data bundle: freqs/strain/psd (see KernelFused.batched_log_likelihood_kernel!'s docstring for the likelihood convention they feed), plus detector (a GravitationalWaveData.Detector, e.g. GravitationalWaveData.H1, for the antenna response and time delay) and gps_time (the FIXED event trigger time, GPS seconds – NOT a sampled parameter; only the small offset t_c sampled as physical-params row 6 is a free parameter, see KernelFused.jl's module docstring for the full row convention). Multi-detector data is a vector of these (see DetectorData).

The 3-argument constructor LikelihoodData(freqs, strain, psd) (for synthetic data where the sky position doesn't matter) defaults to GravitationalWaveData.H1 and GW150914's trigger time (1126259462.4 GPS seconds).

GravitationalWaveBayes.Types.PEConfig — Type
PEConfig{T}(ntime, nwalkers, step_size, nsteps; likelihood options...)

Run configuration for batched parameter estimation: ntime (the frequency-domain grid length every likelihood/kernel call asserts against, e.g. KernelFused.jl's fused kernels), nwalkers (batch size), step_size/nsteps (the sampler's initial leapfrog step and draw count – see NUTSCore.jl's NUTSConfig for the full dual-averaging/adaptation config batched_nuts! seeds with them).

The keyword fields select likelihood variants (all default to the plain likelihood):

  • marginalize_phase::Bool (default false): analytically marginalize the reference phase (row 7) under its uniform [0, 2pi) prior, logL = -1/2(<h,h> + <d,d>) + log I0(|<d,h>|). Exact for waveforms whose phase enters only as a common exp(-i*phase) factor (the dominant-mode-only PAF2Models). The sampled phase row then has zero likelihood gradient and is drawn from its prior; BatchedNUTS.reconstruct_marginalized! redraws it from its conditional posterior afterwards.
  • time_reference::Int (default 0): multi-detector only. 0 means the sampled t_c is the geocenter arrival time; k >= 1 means it is the arrival time at detector data[k] (bilby's time_reference), which decouples t_c from ra/dec. Single-detector likelihoods already treat t_c as that detector's arrival time and ignore this field.
  • marginalize_distance::Bool (default false), distance_lo/distance_hi (Gpc, default 0.05/4.0), distance_power::Int (default 0): analytically marginalize the luminosity distance (row 5) under the prior p(dL) ∝ dL^distance_power on [distance_lo, distance_hi] (2 = uniform in Euclidean volume). Uses <h,h> ∝ dL^-2, <d,h> ∝ dL^-1 and a per-walker Gauss-Legendre quadrature (see KernelFused._distance_marg). Combines with marginalize_phase. The sampled dL row then only carries prior draws; reconstruct_marginalized! redraws it afterwards.
  • time_ref_frequency (Hz, default 0 = off), time_ref_offset (s, default 0): PAF2 models only. When on, the sampled time row is t_ref = t_c + t*(theta; f_ref) + time_ref_offset, where t* is the model's own stationary-phase time at which the GW frequency passes f_ref (for the PAF2 tables, dPsi/df = 2 pi t* exactly). An in-band arrival time is what the data measure; the coalescence time is an extrapolation past the band that slides along a long curved ridge with the masses and spins. The offset is a constant that just re-centres the prior window (e.g. -t* at a reference point).
  • fmax_taper (Hz, default 0 = off): PAF2 models only. Multiplies the amplitude by a C1 sin^2 taper over the last fmax_taper Hz below the table's own end frequency fmax. Without it the signal is cut off exactly at fmax, which moves with the masses/spins, so every time fmax crosses a frequency bin the log-likelihood JUMPS (measured up to ~1 on an SNR-13 injection) – step-size independent energy errors that pin NUTS at tiny step sizes. Injections must use the same taper.
  • phase_ref_frequency (Hz, default 0 = the data's lowest frequency): SEOBNRv5PHM, and IMRPhenomXHM / SEOBNRv5HM on the mode-sum device path (XHM: its phase reference frequency f_ref; SEOBNRv5HM: the modes rotated by the (2,2) orbital phase at that frequency); the sampled phase is then the phase there. The waveform's reference frequency – where the reference phase, the spin components and the inclination frame are defined (pyseobnr's f_ref) – separately from its start (0.9 x the lowest data frequency). A phase defined at a low frequency is coupled to the masses and spins by the whole inspiral phase up to the sensitive band (many wraps across a population: the dominant thin direction of the posterior); defined near the band it is not. Capped at M omega = 0.06 (below the end of any inspiral in the prior).

GravitationalWaveBayes.Types.PEState — Type
PEState{T,A,V}

Sampler state for batched parameter estimation. positions/momenta are 2-D (nparams x nwalkers) device arrays of type A; logp/energy are 1-D arrays of type V.

A and V are independent type parameters (rather than V being derived from A, e.g. via Vector{T}) specifically so that logp/energy can live on the same device as positions/momenta — e.g. A = CuMatrix{T} paired with V = CuVector{T} — instead of being hardcoded to host Vector{T}, which would force a host round-trip on every access. Construct with plain PEState(positions, momenta, logp, energy) and let the type parameters be inferred.

Data conditioning and I/O

GravitationalWaveBayes.DataIO.build_gwdata — Method
build_gwdata(strain_path; trigger_time, duration=4.0, post_trigger=2.0,
             psd_segment=1024.0, f_min=20.0, f_max=1024.0, alpha=0.2, psd_method=:median,
             window_power_correction=false) -> LikelihoodData

Glue GravitationalWaveData.load_gwosc_strain/GravitationalWaveData.condition_segment/GravitationalWaveData.psd/to_frequency_domain into a LikelihoodData, following Jim's tutorial config as the default (4s analysis window / 2s post-trigger, 1024s off-source PSD segment immediately before the analysis window, 20-1024 Hz band).

data.psd is the one-sided PSD in the convention gwpy/bilby/LALInference use – GravitationalWaveData.psd's off-source estimate, or psd_file (two columns, e.g. a PE-release PSD; see read_psd_file) when given. As in bilby >= 2.6.0 it is NOT multiplied by the Tukey window factor mean(w^2): the signal sits in the flat part of the window, where the noise is not reduced (bilby PR #967, issue #869). window_power_correction=true restores the bilby <= 2.5 convention (PSD x mean(w^2), see window_factor; every GWTC-2.1 / GWTC-3 bilby release), like bilby's BILBY_INCORRECT_PSD_NORMALIZATION=TRUE; SNRs are then 1/sqrt(mean(w^2)) higher. KernelFused.jl/RelativeBinning.jl apply the standard 4 * df matched-filter normalization themselves (see KernelFused.batched_log_likelihood_kernel!'s docstring); data.psd does not need to (and must not) have that folded in here.

detector (default GravitationalWaveData.H1) and gps_time=trigger_time are threaded straight into the returned LikelihoodData for the single-detector antenna-response projection KernelFused.jl's kernels now perform – see LikelihoodData's docstring in Types.jl. Explicit here (not relying on LikelihoodData's own 3-arg-constructor default, which happens to also be H1/GW150914's trigger time) so this stays correct for a future non-GW150914/non-H1 call.

GravitationalWaveBayes.DataIO.build_gwdata_multi — Method
build_gwdata_multi(paths::AbstractVector{<:AbstractString}, dets::AbstractVector{Detector};
                    trigger_time, kwargs...) -> Vector{LikelihoodData}

Multi-detector entry point: calls build_gwdata once per (path, detector) pair (e.g. build_gwdata_multi(["H-H1_....hdf5", "L-L1_....hdf5"], [GravitationalWaveData.H1, GravitationalWaveData.L1]; trigger_time=1126259462.4)), sharing trigger_time and every other keyword argument across all detectors – the same physical event, so every returned LikelihoodData entry carries the identical gps_time (required by KernelFused.jl/RelativeBinning.jl's multi-detector methods, which assert this rather than assume it).

length(paths) == length(dets) is required (one strain file per detector). Each detector's freqs/strain/psd are conditioned independently by its own build_gwdata call and are NOT assumed to share a grid across detectors – see Types.DetectorData's docstring.

GravitationalWaveBayes.Priors.GWPrior — Type
GWPrior{T}(; bounds=Dict(), distance=:uniform, masses=:uniform_mc_q, nrows=11)

Prior over the 11-row (or, nrows = 15, precessing: + in-plane spins, see the header) sampled space. bounds maps row names ("mc", "q", "chi1", "chi2", "dL", "t_c") to (lo, hi) overrides of the package defaults; the angular rows keep their natural domains. distance is :uniform or :volume (∝ dL^2); masses is :uniform_mc_q or :components (uniform in detector-frame m1, m2). m1, m2: (lo, hi) detector-frame component-mass constraints (support cuts, as bilby's Constraint priors: the prior is renormalized). source
GravitationalWaveBayes.Priors.GaussianPriorMixture — Type
GaussianPriorMixture(prior, rows, mu, cov; alpha=0.1, rng, nmc=200_000)

Normalized SMC reference density on the 11-row sampled space: q0 = alpha * prior + (1 - alpha) * N_box(x[rows]; mu, cov) * prior(x[other rows]), the Gaussian truncated to the prior box (its in-box mass estimated once by Monte Carlo). The prior component keeps q0's support equal to the prior's, so annealing from q0 stays evidence-exact; the Gaussian concentrates the particles where a cheaper fit (e.g. another model's posterior) put them. rows should be the well-localized, non-periodic rows (intrinsic + tc); the sky/orientation and marginalized rows keep the prior. Sample with [`samplereference](@ref), evaluate with [referencelogpdfand_grad!`](@ref).

source
GravitationalWaveBayes.Priors.KDEPriorMixture — Type
KDEPriorMixture(prior, rows, centers, cov; alpha=0.1, rng, nmc=4000)

cov is one shared bandwidth matrix or a (k, k, K) array of per-kernel ones (see local_kde_covariances).

Normalized SMC reference built from posterior samples of a cheaper analysis: q0 = alpha * prior + (1 - alpha) * (1/K) sum_k N_box(x[rows]; centers[:, k], cov) * prior(x[other rows]). A Gaussian kernel density estimate (shared bandwidth matrix cov) on rows, so unlike a single Gaussian it follows multimodal / curved structure such as a two-detector sky ring. Periodic rows (ra, psi) use the nearest-image difference (accurate while the bandwidth is well below the period); each kernel is truncated to the prior box on the non-periodic rows with its own in-box mass (Monte Carlo, nmc draws per kernel). Evidence-exact as a reference, like GaussianPriorMixture.

GravitationalWaveBayes.Priors.local_kde_covariances — Method
local_kde_covariances(X, centers_idx, period; k=24, h=0.8, floor=0.02) -> Array (d, d, K)

Per-kernel bandwidth matrices for a LOCAL Gaussian KDE over samples X (d x N, rows in sampled coordinates; period[i] > 0 marks periodic rows): kernel j sits at X[:, centers_idx[j]] and gets h^2 times the covariance of its k nearest samples (distance scaled by the global sd per row, nearest image on periodic rows), plus floor^2 times the global covariance so no kernel is degenerate. Unlike one global bandwidth, local covariances follow narrow curved ridges, so draws from the mixture stay near the posterior's support.

Likelihood kernels

GravitationalWaveBayes.KernelFused.batched_log_likelihood_kernel! — Method
batched_log_likelihood_kernel!(ll, params, cfg, data::AbstractVector{<:LikelihoodData};
                                backend = KernelAbstractions.CPU(), model = IMRPhenomD())

Multi-detector method: sums the frequency-domain matched-filter log-likelihood across every detector in data (one LikelihoodData entry per detector, e.g. [h1_data, l1_data]) inside a single kernel launch — still one kernel thread per walker, with an inner for d in 1:ndet loop over detectors (see the multi-detector design note above _extrinsic_setup for the full reasoning). params is (11, nwalkers) for IMRPhenomD/IMRPhenomXAS, (15, nwalkers) for IMRPhenomXP (same PHYSICAL row convention documented at the top of this file, asserted against model here exactly like the single-detector method) — there is one physical event (one m1, m2, ..., one t_c), only the per-detector projection (antenna response) and per-detector arrival-time offset (t_c plus that detector's own GravitationalWaveData.time_delay_from_geocenter) differ.

All entries of data must share the same gps_time (same physical event); this is asserted, not assumed. Each detector's own freqs/strain/psd may have a different length — the inner per-detector frequency loop uses that detector's own grid, not a shared shape.

Dispatches to model isa IMRPhenomD/IMRPhenomXAS/IMRPhenomXP specialized kernel bodies exactly like the single-detector method above (same Enzyme-through-KernelAbstractions reasoning: the scalar-core kernel bodies differentiate, the generic array-based fallback does not); no generic fallback is provided for the multi-detector path since every supported waveform family already has a specialized scalar core and there is no tested Enzyme-safe generic multi-detector kernel body. For IMRPhenomXP, _xp_precession_setup's frequency-independent setup and the aligned-(2,2)-mode ampl_coeffs are hoisted outside the 1:ndet loop (genuinely detector-independent, using the FIRST detector's first frequency bin as f_ref); t0/phi_coeffs/Fplus/Fcross are recomputed per detector since they depend on that detector's own time-delay-shifted t_c and antenna-response geometry — see _fused_waveform_likelihood_kernel_phenomxp_multi!'s own comment block. Relative binning for IMRPhenomXP (single- and multi-detector) is now also supported, see RelativeBinning.jl.

model isa IMRPhenomXHM (params is (11, nwalkers) since this model is aligned-spin/non-precessing, same convention as its single-detector method) dispatches to _fused_waveform_likelihood_kernel_phenomxhm_multi!: _xhm_system_setup/_xhm_mode_setup/ _xhm_mode32_setup (genuinely detector-independent, anchored to the FIRST detector's first frequency bin as f_ref) are hoisted outside the 1:ndet loop, exactly like IMRPhenomXP's setup; Fplus/Fcross and the coalescence-time phase shift are recomputed per detector, since the single-detector kernel's exp(im*2*pi*f*t_c) post-multiplication generalizes to exp(im*2*pi*f*(t_c + dt_geo)) per detector (dt_geo = time_delay_from_geocenter_gmst(det_d, ra, dec, gmst_val), the same per-detector light-travel-time offset every other multi-detector kernel here folds into its own t0 — see _fused_waveform_likelihood_kernel_phenomxhm_multi!'s own comment block for the full derivation/verification).

Relative binning

GravitationalWaveBayes.RelativeBinning.RelativeBinningSetup — Type
RelativeBinningSetup{T,E,C}

Precomputed relative-binning summary data for a fixed reference parameter set theta_ref and a fixed (data, psd) pair. Built once per analysis by build_relative_binning (whose OWN internal computation always runs host-side, reading data.freqs/.strain/.psd scalar-by-scalar – that part is unchanged), then reused for every sampler step via binned_log_likelihood_kernel! – none of these fields depend on the trial parameters being evaluated.

GPU-portability: E/C are free type parameters (mirroring PEState's own {T,A,V} pattern in Types.jl) rather than hardcoded Vector{T}/Vector{Complex{T}} – every build_relative_binning method wraps its freshly-built host arrays in to_device immediately before constructing the returned struct, so E/C become CuVector/CuVector{Complex{T}} under the CUDA extension (same global device-selection convention compatible_array/to_device already use everywhere else in this codebase) and plain Vector/Vector{Complex{T}} otherwise – callers never branch on which backend is active. This is ONLY the "does the array live on the right device for binned_log_likelihood_kernel!'s own kernel launch" concern; build_relative_binning's own setup-time computation (reading data.freqs/.strain/.psd) is still ALWAYS host-side regardless of E/C (data itself keeps its own array type, generally host Vectors even in a GPU-backed NUTS run, since this setup cost is paid once per analysis, not once per leapfrog step – unlike positions/momenta/logp/energy, which genuinely need compatible_array inside the sampling hot loop).

Fields:

  • edges::E: sparse bin-edge frequencies (length nbins+1), a subset of the original dense frequency grid.
  • fm::E: per-bin central frequency (length nbins), the expansion point for the linear ratio fit r(f) ~= r0_b + r1_b*(f - fm_b). NOT itself passed into binned_log_likelihood_kernel!'s kernel launch (kept for external diagnostics only) – still wrapped in to_device for type-parameter consistency with edges/B0/B1, not because the kernel needs it there.
  • href_edges::C: reference waveform h(theta_ref; f) evaluated at each bin edge (length nbins+1) – needed at kernel-eval time to convert a trial waveform's bin-edge values into the ratio r.
  • A0, A1::C, B0, B1::E: the per-bin relative-binning summary coefficients (length nbins each), see this file's header comment for their definition.
  • dd_term::T: the theta-independent -0.5*<d|d> constant, precomputed once so binned_log_likelihood_kernel! reproduces the same likelihood normalization as KernelFused.batched_log_likelihood_kernel!.

GravitationalWaveBayes.RelativeBinning.binned_log_likelihood_kernel! — Method
binned_log_likelihood_kernel!(ll, params, setup::RelativeBinningSetup{T};
                               backend=KernelAbstractions.CPU(), model=IMRPhenomD())

Relative-binning approximation to KernelFused.batched_log_likelihood_kernel!: for each walker j, evaluates the trial waveform only at setup's sparse bin-edge frequencies (via the same non-allocating _phi_coeffs/_phi_scalar/_ampl_coeffs/_ampl_scalar scalar core used by the full-grid fused kernel), linearly interpolates the amplitude/phase ratio relative to the reference waveform within each bin, and combines with setup's precomputed A0/A1/B0/B1 summary coefficients – see this file's header comment for the exact formulas (Cornish 2010; Zackay, Dai & Venumadhav 2018).

data::LikelihoodData supplies detector/gps_time for the antenna-response projection (its freqs/strain/psd are NOT reused here – setup already carries everything derived from those, per its docstring). Same gmst_val = GravitationalWaveData.gmst(data.gps_time)-computed-once-outside-the- kernel pattern as batched_log_likelihood_kernel!; see that function's docstring / this file's module docstring for why ra/dec/psi themselves must still flow in via params and be used INSIDE the kernel body (Enzyme correctness).

Written generically against KernelAbstractions.Backend, same portability caveat as batched_log_likelihood_kernel!: only KernelAbstractions.CPU() is exercised/tested here.

GravitationalWaveBayes.RelativeBinning.build_relative_binning — Method
build_relative_binning(model, params_ref, data::AbstractVector{<:LikelihoodData}; nbins=150)
    -> Vector{RelativeBinningSetup}

Multi-detector entry point: builds one RelativeBinningSetup per detector in data, by reusing the single-detector method above once per detector — NOT a reimplementation. All entries of data must share the same gps_time (same physical event); asserted, not assumed.

Physical reasoning: params_ref's row 6 (t_c) is the coalescence-time offset at the GEOCENTER (shared across detectors, same as the kernel bodies below), but each detector's own reference waveform needs its OWN arrival-time shift, t_c + GravitationalWaveData.time_delay_from_geocenter(detector, ra, dec, gps_time). This function is host-side, one-time setup code — NOT inside a differentiated @kernel body — so it takes the named Detector directly; the kernel bodies below use the isbits geometry(detector) instead (the Detector's String prefix trips Enzyme's activity analysis). For each detector i, a COPY of params_ref with row 6 replaced by t_c + delay_i is passed through the existing, unchanged single-detector build_relative_binning — reusing its already-validated bin-placement/summary-coefficient logic exactly, rather than duplicating it.

GravitationalWaveBayes.RelativeBinning.build_relative_binning — Method
build_relative_binning(model, params_ref, data::LikelihoodData; nbins=150)

Host-side, once-per-analysis setup for relative binning. params_ref is an 11-element vector [m1, m2, chi1, chi2, dL, t_c, phase, ra, dec, theta_jn, psi], the same PHYSICAL parametrization batched_log_likelihood_kernel!/KernelFused.jl consume (see that file's module docstring for the full row convention) – NOT the sampler's (mc, q, chi1, chi2, dL, t_c, phase, ra, sin_dec, cos_theta_jn, psi) layout; convert first if params_ref comes from sampler-space (e.g. via BatchedNUTS._mc_q_to_m1_m2 plus asin/acos for the two reparametrized angles).

The reference waveform href_dense is the FULL detector-frame projection at params_ref – distance-scaled, t_c/phase-shifted, plus/cross-decomposed by theta_jn, and antenna-response- projected via data.detector/data.gps_time – computed with the exact same _extrinsic_setup helper (mirrored in this file, see its docstring) the dense kernel bodies use, so relative binning approximates the SAME likelihood surface KernelFused.jl evaluates on the full grid, not a face-on/no-extrinsic approximation of it.

Bin-edge PLACEMENT (via _phase_equal_bin_edges, narrower at low frequency) is primarily driven by the bare INTRINSIC phase (Phi(_bin_placement_model(model), freqs, mc, eta, chi1, chi2), no t0/phiRef/antenna terms) rather than the full extrinsic phase: this is a heuristic for where the waveform's SHAPE varies fastest (justifying finer bins in the inspiral), and per _bin_placement_model uses a cheap IMRPhenomXAS() proxy rather than model's own Phi for SEOBNRv5AlignedSpinF2 (whose own Phi is a PA-table-backed EOB evaluation, not cheap to run across the full dense grid just for a placement heuristic) – identity for every other model this method handles. Folding in params_ref's OWN actual t_c-driven linear-in-frequency term directly would add a roughly uniform-in-f phase-accumulation rate that scales with however large params_ref's t_c itself happens to be (skewing the heuristic toward uniform spacing for large |t_c|, defeating its purpose) without changing where the intrinsic waveform shape itself varies fastest – so that is NOT what's added.

Instead, a fixed, params_ref-independent SAFETY FLOOR on bin WIDTH (not on placement priority) is applied afterward via _cap_bin_width_for_extrinsic_ramp (see its docstring for the full mechanism and rationale, and for why this is a strictly additive, regression-proof-by-construction post-processing step rather than a change folded into the placement heuristic itself – an earlier version of this fix tried the latter and measurably regressed existing wideband models). It guarantees no bin is wider than the frequency span over which a residual t_c (or per-detector arrival-time) mismatch of up to max_tc_deviation seconds between a NUTS trial point and params_ref would accumulate more than max_extrinsic_phase radians of extra, model-independent phase – which only matters (widens bin count above what the model's own accumulation alone would pick) for a narrow, low-cycle-count band like SEOBNRv5AlignedSpinF2's; for wideband, many-cycle models the model's own gradient already forces bins narrower than this cap almost everywhere, so placement is unchanged for those. The per-bin A0/A1/B0/B1 summary coefficients and href_edges below still use the FULL extrinsic href_dense, so accuracy of the actual relative-binning approximation is unaffected by this choice – only which frequencies get edges.

max_tc_deviation/max_extrinsic_phase (keywords below, BOTH DEFAULT TO 0 = exact pre-fix behavior, opt-in only): see _cap_bin_width_for_extrinsic_ramp's docstring for the exact roles, why the default must stay 0 (a nonzero default would silently collapse relative binning's speedup for every existing model, confirmed not assumed), and the hard native-grid-resolution ceiling on what any setting can actually fix.

Computes the reference waveform on data's full dense frequency grid (data.freqs, one Ampl/Phi call each – this is the only place this module evaluates the array-oriented, allocating waveform API; it runs once, on the host, well outside any hot loop), picks nbins non-uniform bin edges via _phase_equal_bin_edges (narrower at low frequency), and reduces the dense data/reference-waveform/PSD arrays into the A0/A1/B0/B1 per-bin summary coefficients described in this file's header comment.

nbins is a target; see _phase_equal_bin_edges's docstring for when the actual bin count returned (length(result.edges) - 1) can be smaller.
